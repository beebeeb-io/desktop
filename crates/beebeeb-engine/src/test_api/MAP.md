## How a rung drives the fake (wave 2b, slice S7)

Hand-written below the generated table; `make map` on `v2-native` may drop it, so the same text is in the module docs of
`fake_uploads.rs` and the `USAGE` of `server.rs` (`bb-fake-server --help`).

1. **A whole upload completes.** Nothing to call: the engine's own upload client works against the fake. `POST /api/v1/uploads/init`
   (a new file: an id the account does not hold; a new version: an id it holds, with `base_version_number`, a stale base is a
   409), `PUT /uploads/{session}/chunks/{n}`, `POST /uploads/{session}/heartbeat`, `POST /uploads/{session}/complete`
   (a repeat answers `already_completed`), `POST /files/{id}/upload/abandon`, and the picture routes `PUT /files/{id}/thumbnail[/{variant}]`
   and `GET /files/{id}/thumbnail/{variant}`. The fake stores each chunk and the completion name exactly as sent; the file's
   `version_number`, `updated_at` and `size_bytes` move; `GET /sync/ops?since=N` then lists `file_create`, or `file_rename` +
   `file_update` for a version, and the snapshot shows the new row. Not modelled: the in-progress 409, the rename check at `complete`.
2. **Another device saved a newer version.** One HTTP call, no token, to the running `bb-fake-server`:
   `POST /fake-control/newer-version` with a JSON body `{"path": "Documents/notes.md", "content_text": "..."}`
   (or `"file_id"` instead of `"path"`, or `"content_base64"` instead of `"content_text"`). It answers `{file_id, version_number,
   size_bytes, updated_at}`; 404 for no such file, 400 for a missing field, 409 for a folder or trashed file. The new content is sealed with
   the fake account's key for the file by core's chunk encryptor, the name re-sealed with the commitment counter one above the old
   name's, the version number goes up by one, `updated_at` moves, the stored pictures of the file are cleared, and the next
   `sync/ops` reports `file_rename` + `file_update`. In a Rust test: `FakeAccount::push_newer_version(id, bytes)`.
3. **Uploads refused on demand** (off by default). A line `uploads-off` on standard input (stays until the server stops), or
   `POST /fake-control/uploads-refused` with `{"refused": true}` and back with `{"refused": false}`. While on, every
   `POST|PUT /api/v1/uploads/...` is hung up on without an answer (what a client reads as unreachable); every other route answers as before.
4. **A device sign-in (DW-A07 to DW-A10).** Start the app with `--api-base http://127.0.0.1:<port>` and ask to sign in with
   another device: the app's socket (`GET /api/v1/auth/cli`) is served on the same port and the app shows a code. The fake's
   second device answers with one HTTP call, no token: `POST /fake-control/device-approve` with `{"code": "XXXX-XXXX"}` (or
   `{}`: the one waiting request) approves it the way an approving app does (shown the request, a password step-up for that
   code, the claim, the account's key sealed to the app's key); the app ends signed in and unlocked. `{"approver": "stranger"}`:
   another account tries and is refused (403), the request keeps waiting. `POST /fake-control/device-deny` denies it (DW-A09);
   `POST /fake-control/device-code-life` with `{"seconds": n}` (1 to 300) shortens the codes issued after it (DW-A10);
   `GET /fake-control/device-requests` answers `{"waiting": n}`. The routes and the wire: `fake_device_signin.rs`.
