# Plan: what the 0.8.25 bridge release adds for the 0.9.0 jump

For the `main` hotfix lane. Spec: `docs/superpowers/specs/2026-11-11-native-installer-updater.md` §2. Nothing here
is applied on the P1 branch, and **none of this code has been compiled**: it is written against `main` `31a1f949`
(`src-tauri/src/update_window.rs`) and `tauri-plugin-updater` 2.10.1, whose `Update` has public `version: String`,
`download_url: Url`, `signature: String`, and `download(..) -> Vec<u8>` / `install(bytes)` as separate calls.
0.8.25 stays a Tauri build; `release.yml` publishes it as any 0.8.x.

## Changes for lane H1 (2026-11-11, after the security review of PR #283; lane P1b)

Everything below this list is already rewritten to match; this is what moved since the version H1 started from.

1. **Items 4 and 5 are REQUIRED for 0.8.25, both** (they were "recommended"). Either one alone leaves a hole:
   5 without 4 does not bind an old-format artefact to its version; 4 without 5 lets a native build in without a
   signed manifest.
2. **A version that does not parse is refused, in both items, before anything else** (new helper
   `plain_update_version`). Before, `is_native_line` was false for such a version, so item 5 was skipped.
3. **Two keys (Guus, 11:40; new item 6).** Native installers and v2 manifests are signed by the v2 key
   (`src-tauri/updater-v2.pub`, the same bytes as `crates/beebeeb-updater/keys/updater-v2.pub`, key id
   `FED25848C41F2348`), not by the key in `tauri.conf.json`. So item 1 changes shape: **two updater builders, not
   one builder with two endpoints.** The v2 address is asked with `.pubkey(<v2 key>)` and may only yield 0.9.0 or
   later; the legacy address is asked with the configured key and may only yield a version below 0.9.0.
   0.8.25 itself is signed by the old key, by `release.yml`, unchanged.
4. **The crate's API changed** (cherry-pick it again from `native/p1-installer-updater`, at or after the head named
   in PR #283's "Delta 2"):
   - `policy::check(trust, channel, installed, seen, now, manifest, signature)`: a new `now` (unix seconds).
   - `host::windows_release_trust()` is gone for the bridge; use `host::windows_trust_built_at(not_before)`, which
     returns `Result<Trust, NotAReleaseBuild>` and trusts the v2 key only, for 0.9.0 and later.
   - `not_before` on the bridge line is **one fixed constant, `beebeeb_updater::V2_KEY_CREATED`**
     (`1_794_355_200`, 2026-11-11T00:00:00Z, the day the v2 key was made), NOT each build's own time (lead ruling,
     2026-11-11 12:10; this replaces the earlier text of this entry). **No `BEEBEEB_BUILD_NOT_BEFORE` for 0.8.25
     and no `release.yml` change for it.** Do not set that variable in a 0.8.x build at all: the crate's
     `build.rs` stops a build where it is set to something that is not a plausible time. What the constant gives:
     nothing the v2 key did not sign on or after that day is accepted. What it does not give: the bridge keeps no
     replay mark, so a v2 manifest of a WITHDRAWN native build can still be replayed to a 0.8.25 install by
     whoever controls the host; the native build it installs then refuses anything older than itself. Stated.
   - The signed manifest is parsed strictly (unknown or repeated fields refused); `Refusal` has three new values
     (`KeyNotValidForVersion`, `SignedInTheFuture`, `OlderThanThisBuild`). Nothing to do but compile.
   - New dev-dependencies in the crate (`ed25519-dalek`, `rcgen`, `native-tls`): they reach `src-tauri`'s lock
     file only if H1 runs the crate's own tests from that workspace.
5. **The native installer refuses to run over anything below 0.8.25** and reads the version from the uninstall
   entry's `DisplayVersion`: 0.8.25's installer must keep writing a plain `0.8.25` there (it does today).
6. **The hand-off note is now read** (`beebeeb_updater::handoff`): keep item 2's file name and fields exactly
   (`update-handoff.json`; `from`, `to`, `channel`, `at`), `from` and `to` as plain versions, and write it only
   after the checks of items 4 and 5 passed.
7. **macOS:** see "macOS's exposure" under item 4. No code for H1 beyond confirming one fact on `main`.
8. **(Delta 3, 12:10) More crate API, cherry-pick again at PR #283's "Delta 3" head:** `Apply::launch` now takes
   a `&VerifiedInstaller` (not used by the bridge, which installs through Tauri); `host::launch_nsis` is gone;
   `host::windows_release_trust()` no longer fails for a missing build time (the policy refuses instead, with
   `Refusal::NoBuildTime`); `NotAReleaseBuild` has one variant; the crate has a `build.rs`. The bridge calls only
   `policy::check`, `host::windows_trust_built_at(V2_KEY_CREATED)`, `host::SystemClock`, `Channel`, `Version`.
9. **`release.yml` and `sign-macos-updater-artifact.yml`:** PR #283 adds `environment: desktop-release` to the
   macOS signing job and moves its signer install out of the key-holding step. If H1 touches either file, keep
   every job that signs inside that environment and no install in a step that holds a key.

Items 1-3 make the jump possible and clean. Items 4-6 are **required**: they close security finding 1 of the spec
(task 2449) for 0.8.25 and later and make the bridge the only way onto the native line.

## 1. Windows asks the v2 manifest first (v2 key), then the legacy one (0.8.x key)

`src-tauri/src/update_window.rs`, beside `desktop_manifest_path_for_channel`:

```rust
/// The manifest native builds (0.9.0 and later) are published to. Only 0.8.25+ on Windows reads it.
pub(super) fn desktop_v2_manifest_path_for_channel(channel: ReleaseChannel) -> &'static str {
    match channel {
        ReleaseChannel::Stable => "desktop/v2/stable.json",
        ReleaseChannel::Beta => "desktop/v2/beta.json",
        ReleaseChannel::Alpha => "desktop/v2/alpha.json",
    }
}

/// The public key of the native line (0.9.0 and later). The same file as the updater crate's.
pub(super) const UPDATER_V2_PUBKEY: &str = include_str!("../updater-v2.pub");

/// Which release line an address serves, and so which key signs it and which versions it may offer.
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub(super) enum UpdateLine {
    /// `desktop/v2/<channel>.json`: the v2 key, 0.9.0 and later only.
    Native,
    /// `desktop/<latest|beta|alpha>.json`: the key in `tauri.conf.json`, below 0.9.0 only.
    Legacy,
}

/// The lines this build asks, in order. Before a native build exists the v2 address answers 404 and the legacy
/// line serves 0.8.x hotfixes as today.
pub(super) fn update_lines(windows: bool) -> &'static [UpdateLine] {
    if windows { &[UpdateLine::Native, UpdateLine::Legacy] } else { &[UpdateLine::Legacy] }
}

/// True when `version` is one this line may offer. A version that does not parse belongs to no line.
pub(super) fn line_may_offer(line: UpdateLine, version: &str) -> bool {
    match (line, plain_update_version(version)) {
        (UpdateLine::Native, Some(version)) => version >= beebeeb_updater::NATIVE_FLOOR,
        (UpdateLine::Legacy, Some(version)) => version < beebeeb_updater::NATIVE_FLOOR,
        (_, None) => false,
    }
}

/// `MAJOR.MINOR.PATCH` and nothing else, or `None`.
pub(super) fn plain_update_version(version: &str) -> Option<beebeeb_updater::Version> {
    beebeeb_updater::Version::parse(version)
}
```

`updater_builder_for_release_channel` takes the line: one endpoint each, and for `UpdateLine::Native`
`.pubkey(UPDATER_V2_PUBKEY.trim())` on the builder (tauri-plugin-updater 2.10.1 `UpdaterBuilder::pubkey`), so
Tauri's own download check verifies a native installer with the v2 key and a legacy one with the configured key.
The check loop asks each line of `update_lines(cfg!(target_os = "windows"))` in order and takes the first update
for which `line_may_offer(line, &update.version)` holds; an update a line may not offer is skipped and logged by
its line name only (it is not an error for the person: the next line is asked). The chosen line travels with the
update to the install commands (items 4 and 5 need it).

Tests (tables, in the file's existing test module), red first for each row:
- `update_lines`: Windows `[Native, Legacy]`, elsewhere `[Legacy]` (red: the two entries swapped).
- `line_may_offer`: Native takes `0.9.0`, `0.10.2`, refuses `0.8.99`; Legacy takes `0.8.26`, refuses `0.9.0` and
  `9.9.9`; both refuse `0.9.0-beta.1`, `0.9`, `` and `latest`.
- the v2 key: `UPDATER_V2_PUBKEY` is not the key in `tauri.conf.json`, decodes as a minisign public key, and is
  byte-identical to `crates/beebeeb-updater/keys/updater-v2.pub` (one `include_str!` of each, compared).

Consequences to accept: when the v2 address answers an error (5xx) the legacy line answers instead and a 0.8.x
build is offered, which is harmless. A native build served at a legacy address is refused twice: the legacy line
may not offer 0.9.0 or later, and its key does not verify a v2-signed installer.

## 2. Download, pre-flight, record, then install

In `install_update` (and the same in `install_channel_downgrade`), replace `u.download_and_install(…)` and the
lines after it by:

```rust
            let bytes = u
                .download(
                    |_downloaded, _total| {},
                    || lifecycle_log::event(lifecycle_log::LifecycleEvent::UpdateDownloaded { from: versions.0, to: versions.1 }),
                )
                .await
                .map_err(|e| e.to_string())?;
            // The download verified the signature, trusted comment included. Items 4 and 5 go here.
            update_preflight(&app, channel, &from_version, &to_version).await;
            lifecycle_log::event(lifecycle_log::LifecycleEvent::UpdateInstalled { from: from_version, to: to_version });
            #[cfg(target_os = "macos")]
            note_updater_relaunch(&app);
            // On Windows this starts the installer and exits the process; it returns on Linux only.
            u.install(bytes).map_err(|e| e.to_string())?;
            app.restart();
```

`update_preflight` (new, same file). Every step is best effort and bounded: an update must not be blocked by a
pre-flight that hangs, and each failure is logged by a status word only.

```rust
/// What must be on disk before the installer replaces this process (which never returns from `install` on
/// Windows): the channel that served the update, the hand-off note for the next version, and a quiet engine.
async fn update_preflight(app: &tauri::AppHandle, channel: ReleaseChannel, from: &str, to: &str) {
    if let Err(error) = record_installed_release_channel(channel) {
        tracing::warn!(%error, "update pre-flight: could not record the installed release channel");
    }
    write_update_handoff(from, to, channel);
    let quiet = tokio::time::timeout(std::time::Duration::from_secs(10), stop_engine_for_update(app)).await;
    tracing::info!(finished = quiet.is_ok(), "update pre-flight: engine stop");
}
```

- `stop_engine_for_update(app)`: the body of `vault_lock_commands::stop_engine_for_lock` (`vault_lock_commands.rs:615`
  on `main`) without the vault lock: take the runner out of its slot, abort it, then on Windows
  `windows_cf::revoke_callbacks().await` (`CfDisconnectSyncRoot`; it does **not** unregister the sync root), then
  `PRAGMA wal_checkpoint(TRUNCATE)` on the state database. The `main` lane picks the exact runner accessor; this
  plan does not guess it.
- `write_update_handoff`: writes `<state dir>/update-handoff.json` as
  `{"from":"0.8.25","to":"0.9.0","channel":"stable","at":<unix seconds>}` through a temp file and a rename. The
  native app reads it once and deletes it.
- This also fixes spec §8.3: `record_installed_release_channel` used to sit after a call that never returns on
  Windows.

Tests: `write_update_handoff` round trip in a temp state dir (red first: without the rename the file is absent);
the existing `install_guard_tests` stay green. The pre-flight's effect on Explorer is the rehearsal's step 7-10
(`packaging/windows/README.md`), not a unit test.

## 4. Required: an update's signature must name the file and the version it installs (closes finding 1)

Tauri verifies the bytes and, inside the same check, the signature's trusted comment (minisign's global
signature), but never reads the comment. Reading it after a successful `download` costs nothing and ties the
artefact to the version the manifest claims. Right after `download` in both install commands:

```rust
            // First of all: a version that is not plain MAJOR.MINOR.PATCH is not one of ours. Nothing below may
            // be skipped because a version failed to parse.
            if plain_update_version(&u.version).is_none() || !line_may_offer(line, &u.version) {
                return Err(format!("{UPDATE_SIGNATURE_OTHER_FILE_CODE}: this update's version is not one this build installs."));
            }
            if !update_names_its_version(&u.version, u.download_url.as_str(), &u.signature) {
                return Err(format!("{UPDATE_SIGNATURE_OTHER_FILE_CODE}: this update's signature is for another file or version."));
            }
```

```rust
pub(super) const UPDATE_SIGNATURE_OTHER_FILE_CODE: &str = "update_signature_other_file";

/// The file name a Tauri signature signs: `trusted comment: timestamp:<n>\tfile:<name>` (line 3 of the text).
pub(super) fn signed_file_name(signature_base64: &str) -> Option<String> {
    use base64::Engine as _;
    let bytes = base64::engine::general_purpose::STANDARD.decode(signature_base64.trim()).ok()?;
    let text = String::from_utf8(bytes).ok()?;
    let comment = text.lines().nth(2)?.strip_prefix("trusted comment: ")?;
    comment.split('\t').find_map(|field| field.strip_prefix("file:")).map(str::to_string)
}

/// True when the verified signature signs the file the URL ends in, and that name carries the version
/// (`Beebeeb_0.8.26_x64-setup.exe`). An older release's installer, honestly signed, has that release's name.
pub(super) fn update_names_its_version(version: &str, download_url: &str, signature_base64: &str) -> bool {
    let Some(signed) = signed_file_name(signature_base64) else { return false };
    let url_name = download_url.rsplit('/').next().unwrap_or_default();
    signed == url_name && signed.split('_').any(|part| part == version)
}
```

- **Scope:** Windows and Linux (their artefact names carry the version: `Beebeeb_<V>_x64-setup.exe`,
  `_x64_en-US.msi`, `_amd64.AppImage`). The name check is gated with `#[cfg(not(target_os = "macos"))]`; the
  version-parses check above it is not.
- **macOS's exposure, stated.** The Mac updater artefact is `Beebeeb.app.tar.gz`: no version in the name, so the
  name check cannot bind it, and the Mac line reads only the unsigned legacy manifest. Every macOS client,
  0.8.25 included, therefore stays exposed to task 2449 exactly as before: whoever can write the manifest or the
  host can offer an old, honestly signed Mac build as a new version. This plan said "a Mac never installs in
  place (task 2176)"; **H1 confirms that on `main` and writes the answer in its PR**: if the Mac updater only
  opens a download, the exposure is a misleading offer; if it installs, it is the full rollback. **What closes
  it:** (a) for good, the native macOS line, which ships with `beebeeb-updater`'s rules (signed manifest, signed
  name bound to the version, build-time floor) at the same moment as 0.9.0 on Windows; (b) if a Mac 0.8.x
  release is needed before that: publish the Mac artefact under a versioned name
  (`Beebeeb_<V>_aarch64.app.tar.gz`) and drop the `cfg` gate, which is a `release.yml` change and a decision for
  the lead, not part of 0.8.25.
- **Clients that never take 0.8.25** stay exposed to task 2449 on every OS; nothing in a client they do not
  install can change that. They cannot be fed a native installer: it is signed by a key they do not trust.
- **What it closes, also for the old-format manifests:** a manifest that claims `9.9.9` but points at the 0.8.4
  installer with its real signature is refused after the download, before the installer runs. This holds for
  `desktop/latest.json` as much as for v2, so it protects 0.8.25+ on the 0.8.x line too.
- **"Refuse a version lower than the installed one":** the background path already does
  (`should_offer_channel_update`); the manual downgrade is a feature and stays, and with this item a downgrade can
  only install the version it names. What remains open on old-format manifests is a *replay of a whole older
  manifest* (an honest older version offered again): it is a downgrade, so it is never offered in the background.
- Tests (table): the published 0.8.22 signatures pass for their own URL and version (fixture: this branch's
  `crates/beebeeb-updater/tests/fixtures/desktop-latest-0.8.22.json`, 3 of 3 Windows/Linux entries); the same
  signature with version `9.9.9` fails; with another URL basename fails; an error page as signature fails. Red
  first: with the `signed == url_name` half removed, the "other URL" row passes wrongly.

## 5. Required: a native build is installed only from a v2 manifest signed by the v2 key

For an update from the native line, before `install` (the version already parsed and matched its line in item 4,
so this branch cannot be skipped by a version that fails to parse):

```rust
            if line == UpdateLine::Native {
                verify_v2_manifest(channel, &u.version, u.download_url.as_str(), &u.signature).await?;
            }
```

`verify_v2_manifest` does not re-implement the rules: it calls the updater crate, which has no Tauri dependency
for exactly this. That needs `crates/beebeeb-updater` on `main` (cherry-pick it from `v2-native`; it is
self-contained) and, in `src-tauri/Cargo.toml`, `beebeeb-updater = { path = "../crates/beebeeb-updater" }`.

```rust
/// A native build (0.9.0 or later) is installed only when the signed v2 manifest offers exactly this update.
async fn verify_v2_manifest(channel: ReleaseChannel, version: &str, url: &str, signature: &str) -> Result<(), String> {
    use beebeeb_updater::machine::Clock as _;
    use beebeeb_updater::{Channel, Verdict, Version, host, policy};
    let refuse = |why: &str| format!("{UPDATE_MANIFEST_NOT_SIGNED_CODE}: {why}");
    let channel = Channel::parse(channel.as_str()).ok_or_else(|| refuse("unknown channel"))?;
    let installed = Version::parse(real_app_version()).ok_or_else(|| refuse("this build has no plain version"))?;
    let manifest_url = format!("{UPDATE_MANIFEST_BASE_URL}/desktop/v2/{}", channel.manifest_file());
    let manifest = fetch_update_file(&manifest_url).await.map_err(|status| refuse(&status))?;
    let detached = fetch_update_file(&format!("{manifest_url}.sig")).await.map_err(|status| refuse(&status))?;
    let detached = String::from_utf8(detached).map_err(|_| refuse("the manifest signature is not text"))?;
    // The v2 key only, for 0.9.0 and later, and nothing signed before the v2 key existed: the bridge line's
    // not-before is that one fixed day, not a time of its own (it keeps no replay mark either: `seen: None`).
    let trust = host::windows_trust_built_at(beebeeb_updater::V2_KEY_CREATED)
        .map_err(|_| refuse("this build has no v2 key"))?;
    let now = host::SystemClock.now();
    let checked = policy::check(&trust, channel, installed, None, now, &manifest, &detached)
        .map_err(|refusal| refuse(&format!("{refusal:?}")))?;
    match checked.verdict {
        Verdict::Upgrade(offer) if offer.version.to_string() == version && offer.url == url && offer.signature == signature => Ok(()),
        _ => Err(refuse("the signed manifest does not offer this update")),
    }
}
```

`fetch_update_file(url) -> Result<Vec<u8>, String>` is a GET with the app's own client (https, 30 s, no redirect,
at most 1 MiB) whose error is a status word, never reqwest's text. Through `policy::check` the bridge gets every
rule of spec §4 at once: our key on the manifest, the channel's file name, `product` and `channel`, the one
allowed host for the installer (so it must be published under `releases.beebeeb.io`, which the native workflow
does), a length, a signature that names the file and the version, and never below 0.9.0. Any failure returns
`update_manifest_not_signed: …` and nothing is installed. There is no `is_native_line`: the line is known from
the address that answered (item 1), and a version that does not parse was refused in item 4.

Tests: `fetch_update_file` is behind a small trait or closure so the test serves bytes from memory; a manifest
signed with a key generated in the test (dev-dependency `minisign = "0.7"`; no key is committed; the trust's key
is injected in tests) passes; one changed byte fails; a signature under `beta.json` for the stable channel fails;
a signed manifest whose URL differs from the update's fails; a manifest signed before `V2_KEY_CREATED` that
offers a newer version fails. Red first for each. The rules themselves are proven in the crate (PR #283).

## 6. Required: two keys, each for its own line

0.8.25 trusts the key in `tauri.conf.json` for versions below 0.9.0 and the v2 key (`src-tauri/updater-v2.pub`)
for 0.9.0 and later, and never the other way round: item 1 gives each address its key and its versions, item 5
checks the manifest with a trust that holds the v2 key alone. `tauri.conf.json`'s `plugins.updater.pubkey` does
not change, and 0.8.25 is signed by the old key like every 0.8.x, so 0.8.24 and older can install it.
`scripts/check-updater-signature-key.mjs` keeps guarding the 0.8.x artefacts against `tauri.conf.json`; with
`--pubkey-file` it guards the native ones against the v2 file (PR #283).

The native updater applies the same rules itself (`crates/beebeeb-updater/src/policy.rs`); this item makes the
one hop that still runs on Tauri's updater hold to them too.
